# Characters and equipment (M16)

How Zero Return builds what a character wears. Body version **ZR_BLOCK_R15_V1**; one rig for players and AI.

## Body and rig

* **Block body, R15 names.** The owner's Roblox block proportions (`USER_BLOCK_BODY_REFERENCE.png`, scaled ×1.08):
  broad rectangular torso, thick straight limbs, rounded cuboid head. 15 R15-named Blender segments
  (`ZR_BLK_*`, `build_char_base.py`) sized exactly to `RigSpec` (generated by `tools/rig_def.py`).
* **Joints:** the existing Motor6D skeleton and the shared `RigMath` solver are kept (the server writes `C0` for
  the hitbox pose, every client writes `Transform` for animation). No skinned meshes and no second rig.
  Limitation: the head pivots on a block neck, so looking far up with a tall pack is limited (see layering).
* **Outfits are looks, not items.** `Equipment.LOOKS` gives each role its clothing colours and look-level clothing
  (knee pads, armbands, shoulder markers, the Foreman's padded jacket, collar and boot cuffs, scav hoods). The
  body meshes carry neutral vertex colours, and `MeshPart.Color` tints them per look. Scavs have four seeded variants
  (`LookVariant`).

## Equipment is authoritative state

1. The client asks to equip an **owned item instance** (`inv` request: `op`, `g`, `from`, `dest`, and `rev`, the
   equipment revision the request was made against).
2. The server (`Raid.inv` → `Inv`) checks:
   * ownership: the item's holder ref must be `me` or an opened container;
   * location and searched state, and the character's state (alive, not queued, not deploying, raid containers
     only in a raid);
   * slot and kind (`Items.SLOTS`);
   * compatibility (`Equipment.conflict`, plus the armoured-rig rule);
   * the revision: a stale `rev` gets `STALE_REVISION`.
3. Every slot write goes through `Inv.setSlot`, which bumps `holder.erev`.
4. `Appearance.apply` resolves the holder's slots plus the look into worn pieces. It rebuilds only the slots whose
   signature changed, and sets the `Gear_<slot>`, `Look`, `LookVariant`, `AppearanceRev`, `NeckUp` and
   `BodyVersion` attributes. These replicate to everyone, late joiners included.
5. Clients never send mesh IDs, visual keys or armour values. Unknown request fields are ignored, and protection
   always comes from `Items` (`Health.armorFor` reads the holder, never a mesh).

## Worn pieces

* Every piece is a Blender MeshPart from the `ZR_CharGear` / `ZR_CharBase` batches, authored in its **host part's
  space** (origin = host centre). It goes at `host.CFrame * CFrame.new(AssetMeta[key] * scale + shift)` and is
  welded with a `WeldConstraint`.
* Pieces are unanchored and massless, with `CanCollide`, `CanQuery` and `CanTouch` all false. Shots pass through
  packs and pouches to the body parts; hit regions are only the body parts (`Health.PART_OF`).
* **Fallback:** if a mesh is not in the library yet, the piece is a plain box of the right size (logged once).
  `Assets` retries failed batches. When one arrives, `Appearance.reconcileAll` rebuilds every fallback group from
  the holder's *current* state, so the latest equipment wins and protection is unchanged.

## Layering (no clipping between layers)

The torso stack goes outfit overlay (padded jacket) → armour (soft vest, carrier, armoured rig) → chest rig. Each
layer is authored directly on the 2.16 × 1.70 × 1.08 torso. The resolver scales it about the torso centre by the
**shells** (front, back, top, side) of the layers under it (`Equipment.SHELLS`), so a chest rig over a carrier grows
just enough to clear it.

* **Strap lanes:** armour and rig straps run at |x| 0.55–0.58 over the rounded shoulder edge; backpack straps run at
  |x| 0.9, outside every armour panel.
* **Backpacks** move back by the worn shells. The shared pack straps end inside every pack body.
* The **body camera** moves forward by the worn front shells.
* **Slung long guns** lie flat across the back, over the outermost back gear (`Equipment.backExtent`).
* **Tall packs** set `NeckUp`. `RigMath.spine` caps the neck when looking up and the waist takes the rest, so the
  helmet does not sink into a raid pack.

## Compatibility and covered regions

| Rule | Where | Code |
|---|---|---|
| Full-cut helmet (Shell, Bulwark) leaves no room for a headset | `VIS.HELMET_C2/C5.blocks.ears` | `HELMET_COVERS_EARS` |
| Hard hat brim blocks a headset | `VIS.HARDHAT_FOREMAN.blocks.ears` | `HARD_HAT_BRIM` |
| Armoured rig cannot be worn with body armour | `VIS.RIG_PLATE.blocks.armor` and `Inv.canEquip` | `ARMOR_CONFLICT` |
| Headset band goes behind the neck under any headwear | `VIS.HEADSET_*.underHeadwear` | (variant) |
| A backpack covers the chest rig's X harness and a hood worn down | `covers = { upperBack, hood }` | (hidden, restored when the pack comes off) |
| The Foreman's jacket conceals his armour | `LOOKS.foreman.covers.armorVisual` | (internal plates not shown) |

variant.

## First person

* The local client hides every part of its own character (`LocalTransparencyModifier`, `Camera.luau`). The set
  follows parts as they are added and removed, so it does not grow with equipment changes. Other clients still see
  the gear.
* Viewmodel sleeves are the `ZR_FP_Sleeve` / `ZR_FP_Cuff` block meshes, and their colours come from
  `Equipment.fpColors(Look, LookVariant)`, the same table as the third-person body. Gloves take the look's glove
  colour.
* An equipped headset (`Gear_ears`) makes other people's footsteps louder and carry further, and roughly halves
  deafness from blasts and stun charges.

## Adding an item

1. Model the piece in `build_char_gear.py`, in its host part's space, keeping to the strap lanes. Run the batch and
   preview it with `preview_presets.py`.
2. Upload it (`zr_upload.py`). Put the batch ID in `AssetIds.luau`, the centre in `AssetMeta.luau`, and the size in
   `Equipment.SIZE`.
3. Add the item to `Items.luau` (kind, slot, stats) and its visual to `Equipment.VIS` (pieces, layer and shell,
   blocks, covers).
4. Run `ZR_Dev:Invoke("chartests")` and `("tests")`, and check the item in the showroom (`showroom` with `gear`).
